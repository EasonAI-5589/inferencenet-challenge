## 当前网站与需要保留的约束

[现有官网](https://easonai-5589.github.io/inferencenet-challenge/) 是原生 HTML、CSS、JavaScript 静态站点，具有中英文、浅色与深色主题，以及六项主导航：Home、Challenge、Harness、Self-evolving、Leaderboard、Teams。两个赛道另有详情页，总计八个内容页；旧 Data 和 Agent 地址作为兼容跳转保留。

现有页面已经具备本地字体、图表、视频、研究证据和交互基础。主要设计问题是首屏叙述较长、卡片与长段落密度接近、页面之间的视觉节奏和阅读层级还不够明确。这里的判断来自页面阅读与浏览器观察，尚未进行访客测试。

| 约束 | 后续改版要求 |
|---|---|
| 站点定位 | 保留 Global InferenceNet Initiative 的背景、InferenceNet Challenge 的主标题，以及 Business、Finance、Social Science 的研究范围。首页需要同时表达社区、挑战、评估、训练与改进方向。 |
| 事实与发布状态 | 具体比赛日期、正式规则、奖项和提交渠道按现有已确认状态展示。拟议时间与已开放状态分开。 |
| 研究结果 | Dev100 / v10 是开发集结果；业务任务分数是 pilot rubric 结果；Self-evolving 是独立开发研究。它们的分母、缺失值、协议、来源和局限不能被视觉简化抹去。 |
| 数据范围 | 研究数据源、Selected_1000、Dev100 和录制演示任务是不同范围。task 0001 不可写成已经确认属于 Dev100。 |
| 提交系统 | HF 私有仓已经初始化，但提交 UI 仍为本地原型，认证、上传受理与评测服务尚未上线。新导航或 CTA 必须反映该状态。 |
| 参与入口 | 目前官网六类参与路线与提交系统拟议的三类提交入口需协调；不能仅为排版删除路线，或把未来入口标记为可用。 |
| 语言与主题 | 英文正文位于 HTML；中文位于各页词典。改动同步覆盖两种语言和两种主题，保留用户切换偏好。 |
| 桌面范围 | 沿用 README 的桌面开发与验收范围；移动端适配与测试需另行提出。窄桌面窗口仍需可读。 |
| 导航与公开边界 | 保留有效深链接和兼容跳转。公开网站继续只使用已审核的摘要、图表和素材。 |

## 竞品的视觉方法

SimuWorld 使用深色背景、清晰的大字层级、按世界区分的强调色，以及市场和城市主题的图形。品牌气氛先吸引读者，后续章节则用统一的编号、卡片、时间线和规则块降低理解成本。

| 观察到的设计 | 发挥的作用 | InferenceNet 的迁移方向 |
|---|---|---|
| 近黑背景、浅色正文、少量高亮 | 大幅图形和重点按钮保持清楚的前后层次 | 定义背景、容器、边框、正文、次级文本、强调色的语义变量，并同时设计浅色主题。 |
| 展示字体、正文字体与等宽字体分工 | 标题建立品牌，正文负责阅读，标签表达技术与精确性 | 先利用现有 Inter 与 Space Mono；只有高保真比较证明需要时才增加展示字体。 |
| 不同世界使用不同强调色 | 阅读者在多个页面之间仍能识别赛道归属 | 为两个挑战建立稳定的颜色和图形线索；模型系列、状态色与赛道色分别定义。 |
| 有语义的图形和背景 | 金融曲线与城市空间帮助解释任务所处的环境 | 使用任务材料、执行工具、交付物、验证结果等真实结构形成自己的图形语言。 |
| 章节编号、重复的标题结构 | 长内容有明确位置感，便于跳读 | 每节保留一个问题、一句结论、一个主体图或比较结构，再提供展开细节。 |
| 赛道卡片扩大与背景压暗 | 鼠标悬停时突出当前选择 | 用于两赛道选择或案例切换；键盘聚焦也应表达同等信息，正文无需等待动画。 |
| 固定导航与滚动后的背景变化 | 首屏保持开阔，深入阅读后仍能找到入口 | 优化现有导航、章节定位和阅读进度，减少多层导航与阅读提示的重复。 |

浏览时记录的样式样本：背景 `#050608`，正文 `#eef2ee`，次级文本 `#8b958f`；总览使用浅蓝，HoloBit 使用绿色与青色，城市赛道使用紫色与粉色；卡片圆角约 14px。字体分工是 Space Grotesk、Inter、JetBrains Mono。这些是竞品样本，不是 InferenceNet 的最终 token。

[赛道选择页](https://adamleopold.github.io/simuworld-challenge/tracks.html) 是三个倾斜面板构成的全屏入口，具有约 1.4 秒的面板过渡。它适合营造选择世界的体验；在我们的研究内容页面，交互反馈应更短，阅读应更直接。视觉迁移要落到层级、图形语义和组件一致性，具体字体、倾斜构图和配色可以重新设计。

## 竞品如何安排故事

已查看四个主要页面及站内教学演示。以下覆盖站内叙事与演示交互，外链平台未做完整功能验证。

| 页面 | 阅读顺序 | 值得迁移的叙事机制 |
|---|---|---|
| [Overview](https://adamleopold.github.io/simuworld-challenge/index.html) | 提出挑战 → 经济世界模型基础 → 参与过程 → 三赛道与两个世界 → 时间与组织者 | 先让访客理解意义，再解释机制和选择，最后给出行动入口。 |
| [Tracks](https://adamleopold.github.io/simuworld-challenge/tracks.html) | 直接比较三个角色与目标，进入对应赛道 | 用一屏帮助访客完成选择，承担入口职责。 |
| [HoloBit](https://adamleopold.github.io/simuworld-challenge/holobit.html) | 市场任务 → 模拟环境 → 策略与风险 → 参赛流程 → 评分 → 公平规则 → 时间与 FAQ | 把“要做什么、交什么、如何判断成功”展开成连贯路径，减少参赛的不确定性。 |
| [Agentic City](https://adamleopold.github.io/simuworld-challenge/agentic-city.html) | 具体城区与目标 → 如何规划 → 提交产物 → 评估 → 参与者路径 → 引擎与资源 → 时间和 FAQ | 用真实空间、操作示意和产物格式，把抽象的智能体能力变成可想象的工作。 |
| [Lending 教学演示](https://adamleopold.github.io/simuworld-challenge/demo/lending.html) | 设置环境 → 比较两种策略 → 查看动作和结果 → 理解得分 | 让读者通过一次交互理解因果关系。它明确是浏览器本地教学模型，与正式环境和评分分开。 |

竞品最完整的故事结构可以概括为：**意义 → 世界与规则 → 我的任务 → 我的产物 → 如何评价 → 如何开始。** 页面上的图形与交互分别承担其中一步，而每页末尾继续把用户引向下一个行动。

我们的长页可以沿用这一结构。研究方法、详细配置与来源应在读者知道它们为什么重要之后出现；各赛道统一回答任务、输入、过程、产物、评估五个问题，再展示自身差异。

## 建议的视觉系统

建议方向是深墨蓝、冷白和适量青蓝强调色，配合清晰的科研图形与任务材料。浅色主题作为同等完整的阅读界面。品牌色只承担品牌与主要行动的职责；错误、成功、等待以及图表系列使用各自的语义变量。

以下数值用于第一轮桌面设计稿比较，不作为已经验证的标准：

| 项目 | 起始方案 | 验证重点 |
|---|---|---|
| 内容宽度 | 1440px 桌面画布上最大宽度约 1248px，12 列，24px 列间距 | 长表、图示、导航在窄桌面窗口中仍有合理布局。 |
| 空间 | 8px 基础单位，常用 16、24、32、48、64、96px | 段落、组件和章节的间距能够表达不同层级。 |
| 字号 | 首屏 64–80px，章节 36–48px，卡片 24–28px，正文 16–18px | 中英文分别检查换行、行长与行距，不机械套用同一高度。 |
| 字体角色 | 展示、正文、数据与代码标签 | 等宽字体集中用于配置、版本、数字和代码，不覆盖长篇中文。 |
| 容器 | 页面底色、普通区域、重点区域形成少量层级 | 用留白和分隔表达结构；只对需要分组的内容加卡片。 |
| 交互 | 常规反馈约 160–240ms，章节进入约 400–650ms | 减少动态效果偏好下内容完整可见，连续操作不受过渡阻挡。 |
| 组件 | 按钮、链接、标签、赛道卡片、图注、来源、状态、表格采用统一规则 | 悬停、聚焦、选中和不可用状态具有一致含义。 |

优先在共享样式中建立 token，再让页面消费这些变量。现有本地字体和 SVG 工具足以支持首轮改版，当前方案没有迁移框架的依赖。

## 建议的首页故事与布局

首页负责让首次访客理解项目、看到具体工作并找到下一步。详细协议和完整研究报告继续由对应页面承担。以下是待设计验证的顺序：

| 顺序 | 访客要理解的问题 | 建议内容与布局 | 后续入口 |
|---|---|---|---|
| 1 首屏 | 这是什么，与我有什么关系？ | 项目名称、Initiative 背景、一句明确的挑战说明、简洁的任务过程主视觉、机构信息；突出一个主行动和一个次行动。 | 挑战介绍、代表案例 |
| 2 两个挑战 | 我能做哪类工作？ | 两张结构相同的赛道卡：目标、输入、交付物、评估方式与当前状态；用图形和强调色区分。 | 两个赛道详情页 |
| 3 代表案例 | 智能体实际做了什么？ | 一个可以逐步阅读的案例摘要，配合已有录像；通过切换展示另一类任务。 | 完整录像、公开证据 |
| 4 评估与结果 | 结果如何被判断，可信范围是什么？ | 展示评估结构、来源与开发结果入口。首页是否显示数字由设计稿验证；保留数据版本与结果性质。 | Leaderboard 与方法说明 |
| 5 建设与改进 | 我怎样构建或改进智能体？ | 简述 model、harness、environment、evaluator 的关系，再连接研究方向和已有资源。 | Harness、Self-evolving |
| 6 社区与参与 | 谁在组织，我现在可以做什么？ | 保留 Initiative 的四项目标与六类参与路径，按阅读层级安排；状态、资源与联系信息清楚可见。 | Teams、参与说明、将来的真实提交服务 |

当前首页没有榜单，也不加载榜单资源；第四节首先采用评估解释与链接。只有在明确选用公开摘要数字时，才增加相应数据依赖，避免复制一套失去版本约束的结果。

首轮制作三个高保真场景：首屏、两个挑战的选择区、代表案例。它们应使用相同的字体、空间和颜色规则，放到同一完整桌面页面中检查阅读连续性。

## 用真实案例建立差异

最有价值的新增体验是可交互的公开案例摘要：**任务与材料 → 执行与证据 → 检查和修改 → 交付物 → 独立评估。** 图形中的每个节点都应对应真实角色或材料，而每个可选择步骤都应改变读者正在看的信息。

建议在左侧显示阶段与简短解释，右侧显示该阶段的公开材料、输出摘要或结果；视频保持原生播放控制，并提供完整观看入口。任务的目标流程与实际录制路径必须区分，步骤缺失或失败也是结果的一部分。

现有 task 0001、Finance、HR 录像和公开 provenance 可作为候选来源。先核实可公开的逐步证据是否足够，再选择案例；缺少可追溯材料时，使用已验证录像与文字摘要，不补造执行事件。交互展示要明确标识“录制回放”或“公开案例摘要”，不暗示正在运行模型。

竞品教学演示通过策略对比解释一个机制。InferenceNet 可以进一步让访客看到真实交付工作如何被独立评估，以及失败来自哪里。这是建议验证的差异化方向，不能在发布文案中预先宣称已优于竞品。

| 团队 | `teams.html`、`teams.css` | 统一人物、机构、合作方和联系方式的层级，保留已确认的身份与排序。 |
| 翻译 | `assets/i18n/*.zh.json`、`language.js`、`language.css` | 同步改正文、键名和中文；共享资源或词典变动时更新相应 `?v=` 标签。 |

## 分阶段交付与验收

建议按可独立评审的改动推进，每个阶段保留一张完整桌面截图和对应页面链接：

1. **设计基线与首页结构。** 先整理现有页面截图和组件，形成 token 表、首页线框，以及首屏、双挑战、代表案例的高保真设计。使用真实文案长度，检查中英文与两种主题。
2. **首页与共享组件实施。** 在现有静态架构内实现已选方案，同步翻译、版本标签、锚点和图形替代内容；沿用现有预览服务约定。README 中预览脚本是另一台机器的绝对路径，在当前机器先定位有效服务，不能照抄路径或随意终止占用服务。
3. **案例与其他页面扩展。** 在证据范围确认后制作交互案例，再将组件与叙事规则推广至挑战、技术长页、结果页和团队页。未来提交入口的上线依据提交系统 handoff 中的真实实现状态。

验收关注四类结果：

| 类别 | 检查方法与标准 |
|---|---|
| 视觉一致性 | 对照旧版、设计稿和实现，在相同桌面尺寸检查字体、留白、图形、状态与节奏；同时检查较窄桌面窗口以及四种语言和主题组合。 |
| 理解与任务完成 | 首轮邀请约五名首次接触项目的读者，观察能否解释两个挑战、找到演示、定位指标含义与来源、找到参与方式。记录误解和操作障碍；这是形成性测试，不代表统计上证明超过竞品。 |
| 内容与功能 | 导航、深链接、主题、翻译、视频控制、表格排序、图表替代内容和键盘聚焦按实际改动验证；数值、来源与发布状态保持准确。 |
| 性能与可读性 | 将 LCP ≤ 2.5 秒、INP ≤ 200ms、CLS ≤ 0.1 作为目标；现场数据按桌面访问的第 75 百分位判断，实验室测量只用于诊断。普通文本对比度至少 4.5:1，大文本至少 3:1；动态效果支持减少动态效果偏好。 |

性能定义来自 [Core Web Vitals](https://web.dev/articles/vitals)，文本对比度来自 [WCAG 对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。这些是后续目标，本次文档交接没有测量或宣称官网已达到它们。

实际修改网站时，按 README 运行 `node scripts/check.mjs` 和受影响的现有测试，检查本地预览，再提交 PR。当前检查器含依赖正斜杠的路径比较，在原生 Windows 上可能误报；遇到该问题应明确记录环境原因，使用适配的执行环境，不能把修改检查器混入设计文档提交。

本次交接完成后，可直接从设计基线和首页结构开始。首轮需要通过设计稿确定的是：品牌色与字阶、首屏文案和主行动、首页各节篇幅，以及第一个案例的公开证据范围。
