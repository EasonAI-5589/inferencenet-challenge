# 提交服务器与域名 Handoff

日期：2026-10-22（Asia/Shanghai）。目标仓库：`EasonAI-5589/inferencenet-challenge`。前置文档：[提交系统 Handoff（2026-10-21）](2026-10-21-submission-intake.md)、[提交格式 v0.1.0](../submissions/SPEC.md)、[页面与 API 设计](../submissions/API-DESIGN.md)。

**本文记录提交入口改为“自有服务器受理并存储”的方向，并把域名、DNS、HTTPS 和服务器基础配置交给下一位 agent。** 本 PR 只加文档：服务器、域名、证书和提交服务都尚未配置或部署，官网卡片也未改动。

本仓库是公开仓库。服务器 IP、SSH 账号、云账号、DNS 账号和任何令牌都不写进本仓库、Issue 或 PR。

## 与 2026-10-21 设计相比的变化

| 项目 | 2026-10-21 设计 | 当前方向 |
|---|---|---|
| 提交文件的主存储 | 受理服务写入三个私有 HF 提交仓，回执写入 `evaluation-results` | 存在自有服务器的数据盘和数据库。HF 归档改为后续可选：用于异地备份，或审核后发布公开版本 |
| 提交服务位置 | 未定（`SUBMIT_ORIGIN` 待部署时确定） | 自有服务器，经域名和 HTTPS 对外提供 |
| 登录 | HF OAuth / OIDC | **未定。** huggingface.co 在中国大陆无法直接访问，国内提交者不能依赖 HF 登录。建议以邮箱验证码为主，HF / GitHub 登录为可选 |
| 用户直接上传到 HF | 未讨论 | 不采用。私有仓不接受外部用户写入；给用户写令牌会越权；公开仓或公开 PR 会泄露参考答案、oracle 与原始日志。若 Harness 本身开源，可考虑只提交公开仓库链接加固定 commit |

API-DESIGN 中以下内容仍然适用：三类提交与固定路由、共用表单组件、manifest 与 bytes/SHA256 规则、逐文件上传、`Idempotency-Key` 幂等、所有权与 404 规则、`complete` 不执行任何提交代码、执行 worker 与受理服务分离。状态机中的 `storing_artifact` / `archiving_receipt` 改为写入本机存储和数据库；若以后启用 HF 归档，再按原设计补回跨仓恢复逻辑。

## 目标架构

```text
用户浏览器
  ├─ 浏览官网 → GitHub Pages（不变）
  └─ ②③⑤ 提交 → https://<SUBMIT_HOST>/submit/<type>/
                   提交服务器（同一 origin 提供表单页和 /api/v1/）
                     ├─ 反向代理：HTTPS、请求体大小限制
                     ├─ 受理服务：登录、上传、校验、回执、状态
                     ├─ 数据库：owner、版本、幂等记录、状态（只监听本机）
                     └─ 数据盘：已封存的提交包与回执
                   定期备份 → 另一台机器或对象存储
```

- 官网继续由 GitHub Pages 提供。提交服务验收前，v2 首页和 Challenge 页的 ②③⑤ 卡片不改链接。
- 提交页和 API 同 origin，使用服务端会话，避免跨站 Cookie 与 CORS 问题（理由见 API-DESIGN §1）。
- 这台服务器只受理和存储，**不运行任何提交者代码**。以后的自动评测（Docker、Harbor、模型调用）使用另一台机器，并且不持有这台服务器的写权限。

## 服务器规格建议

| 项目 | 建议 | 说明 |
|---|---|---|
| CPU / 内存 | **2 核 4 GB** | 受理服务、数据库、反向代理同机即可。1 核 2 GB 可用于灰度，但多人同时上传时内存偏紧 |
| 系统盘 | 40 GB 以上 | 与数据盘分开 |
| 数据盘 | **100 GB 起**，可扩容 | 单次提交上限 1 GiB；常见包为几十到几百 MB。上传按流写盘，不整体读入内存 |
| 带宽 | **入站 10 Mbps 以上** | 用户上传占用入站带宽。按 3–5 Mbps 计费的机器上传 1 GiB 约需半小时。购买前向云服务商确认入站限速 |
| 系统 | Ubuntu 24.04 LTS（建议） | 下一位 agent 可按实际机器调整 |
| 备份 | 数据库每日导出，数据盘定期同步到异地 | 单盘损坏即丢数据；备份目标不放在同一台机器 |

## 为什么需要域名

- **HTTPS**：官网是 HTTPS 页面，浏览器会拦截从 HTTPS 页面到 `http://<IP>` 的请求；上传和登录本身也必须加密。常用的免费证书签给域名，IP 证书有效期短、配置麻烦。
- **登录回调**：邮箱验证链接、HF / GitHub 登录回调都需要固定的 HTTPS 地址。
- **可信度**：提交者不会愿意把未公开材料传给一个裸 IP。
- **迁移**：换服务器只需改 DNS，不必改官网和文档里的链接。

建议主机名使用 `submit.<已有域名>`。能用学校或项目已有域名的子域名最好；否则新购一个域名。

## 开始前需要用户确认的事项

| 决定 | 影响 |
|---|---|
| 服务器位置：中国大陆或境外 | **大陆服务器的域名必须先完成 ICP 备案**（通常数周，需要备案主体），未备案时云服务商会封禁 80/443 访问。境外（香港、新加坡等）无需备案，但大陆用户访问可能较慢 |
| 使用哪个域名、谁持有 DNS 管理权限 | 下一位 agent 需要能添加解析记录，或由持有人按本文代为添加 |
| 主机名（建议 `submit.<domain>`） | 写入后续部署配置 `SUBMIT_ORIGIN` |
| 登录方式 | 若用邮箱验证码，还需要发信服务及发信域名的 SPF / DKIM / DMARC 记录 |
| 灰度名单和管理员 | 影响应用阶段的 allowlist 与审核角色，不阻塞本次基础配置 |

## 下一位 agent 的任务：域名、DNS 与服务器基础配置

**范围内：**

1. **登记服务器信息**：位置、规格、系统、数据盘大小、带宽、是否有 IPv6。只记录在私有位置，不写进本仓库。
2. **DNS**：为 `<SUBMIT_HOST>` 添加 A 记录（有 IPv6 时加 AAAA）指向服务器。配置期 TTL 设为 300 秒，稳定后可调高。可选添加 CAA 记录，限定签发证书的机构。
3. **系统与 SSH**：更新系统；创建非 root 的运维账号；SSH 只允许密钥登录，关闭密码登录和 root 直接登录；开启自动安全更新。
4. **防火墙**：只对外开放 80、443 和 SSH 端口；数据库等内部服务只监听本机。云厂商安全组和系统防火墙都要设置。
5. **反向代理与 HTTPS**：建议 Caddy（自动申请和续期 Let's Encrypt 证书）；也可用 Nginx 加 certbot。HTTP 自动跳转到 HTTPS。证书确认稳定后再开启 HSTS。
6. **上传相关的代理设置**：请求体上限不低于单文件上限（暂定 1 GiB）；读取超时足够长，慢速网络上传大文件不会被中途断开；Nginx 需设置 `client_max_body_size`，并关闭请求缓冲（`proxy_request_buffering off`），让应用自己流式写盘。
7. **数据盘**：挂载到固定目录（例如 `/srv/inferencenet-submit/data`），写入 fstab 保证重启后自动挂载；归属一个专用的非 root 服务账号。
8. **占位页**：在应用上线前，`/` 返回“提交服务即将开放”的静态页面，`/healthz` 返回 200，方便验证域名和证书。
9. **大陆服务器**：ICP 备案需要用户以备案主体办理，备案完成前不要对公网开放 80/443。agent 只整理所需材料清单。

**范围外：** 部署提交服务应用、建数据库表、注册 OAuth 应用、配置发信服务、修改官网卡片链接、把任何凭据写进仓库。

## 验收标准

- `https://<SUBMIT_HOST>/healthz` 返回 200，证书有效且主机名匹配；尽量分别从大陆和境外网络各测一次。
- `http://<SUBMIT_HOST>/` 跳转到 HTTPS。
- 证书续期可用：Caddy 日志显示自动续期已配置，或 `certbot renew --dry-run` 通过。
- 从外部扫描只看到 80、443 和 SSH 端口；SSH 密码登录被拒绝。
- 数据盘已挂载到约定目录，重启后仍然挂载，服务账号可写、其他普通账号不可写。
- 反向代理的请求体上限和超时已按第 6 条设置。应用部署后，再用 1 GiB 测试文件做一次端到端上传验证。
- 完成后补一份简短的 Handoff，写明主机名、所选代理、数据目录、备份方式和未完成项，不写 IP 或任何凭据。
