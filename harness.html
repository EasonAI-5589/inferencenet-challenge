Harness · Architectures

The harness, part by part.

In InferenceNet an agent is a model working inside a harness: the code that builds each request, runs the tools, keeps the history and decides when to stop. This page takes apart the harnesses InferenceNet evaluates, at the versions it pins, and shows how each one is wired to the same tasks, sandbox and scorer. How a harness is then changed is the subject of the Evolution page.

01 / Lineup

Two harnesses, two designs

DeepAgents is LangChain’s library harness: middleware wrapped around a LangGraph loop, running inside the caller’s Python process. DeepSeek Harness is DeepSeek’s plugin harness: a separate runtime in which every part, the agent loop included, is a plugin. More harnesses will be added here in the same format.

Counts describe the harness, not a run. The DeepSeek Harness counts are read from the pinned bundle and profile files; the DeepAgents counts come from the pinned package and an offline build of InferenceNet’s DeepAgents agent, without a model call.

02 / Anatomy

What every harness decides

Under very different machinery, every harness answers the same questions: once when it is assembled, then again on every step. The comparison below takes up most of these concerns, so a new harness can be added as one more column.

  • Before the model call

    • assembly
    • system prompt
    • history
    • compaction
    • instructions

    How the harness is put together, what the model is told, and how much of the past it still sees.

  • Around the model call

    • request
    • route
    • retries
    • streaming
    • budget

    How one request is built, sent, retried and accounted.

  • After the model call

    • tool routing
    • tool policy
    • sandbox
    • subagents
    • state
    • stopping

    Which tools run, with which permissions, where the result is kept, and when the run ends.

DeepAgents 0.7.13 Python library

How DeepAgents is assembled

  • In 0.7.13 the default stack has no write_todos tool. Among the built-in profiles only the Codex one adds it, through TodoListMiddleware; for any other model the caller has to add TodoListMiddleware.
  • Upstream main (0.7.23) moves SkillsMiddleware from the outermost core position to the tail, after profile middleware and before prompt caching, and adds UnsupportedContentMiddleware after HumanInTheLoop, just before _ToolExclusionMiddleware.
  • A missing tool points to middleware assembly, a profile’s excluded_tools, or, for execute and delete, a backend without that capability. A visible tool that fails points to permissions or the backend itself.

DeepSeek Harness 0.1.5-rc.1 Node runtime + Python SDK Developer preview

Plugins around a log

DSH has no fixed core. At startup the dsh launcher reads a profile, applies its bundles and patch files in order, and mounts the result as a tree of Cordis plugins. The agent loop is one of these plugins: it derives every model request from an append-only session log, and other plugins intercept each phase through events.

How DeepSeek Harness is assembled

  • The loop has no step, turn or recursion limit. maxParallelToolCalls (10) only caps concurrent tool calls, so a deployment that needs budgets enforces them outside the loop.
  • The stock sdk profile is dsh-base plus dsh-sdk-app: 86 rows, 81 of them enabled on Linux and macOS. sdk-minimal is a separate 31-row tree with one platform-selected persistent shell tool (bash, or PowerShell on Windows) and runtime invariant checkers.
  • Upstream master (0.2.1-alpha.2, d7432673) adds a developer/message event and a tool role, refreshes the runtime context on every attempt, replaces the {{cwd}} prompt variable with a working-directory service, removes the invariant checkers and moves sessions to format v4.
  • A missing tool points to the composed tree: dsh --profile <name> --dump-config prints every row with the layer that last patched it. A visible tool that fails points to its provider or a policy plugin.

Package names omit the @deepseek-ai/ scope. Removed from sdk-minimal (19 rows): the DeepSeek API adapter with its request-extension registry and two extensions, the process sandbox and its policy, the subprocess, PTY and terminal backends, the persistent bash and PowerShell tools, background jobs, the session title, and the runtime invariant registry with its four checkers. Without them, run_python is the only tool the model can call.

One DSH step, in order

The loop writes each phase of a step to the session log and leaves the gaps between phases open to other plugins through events. Below, one step of an InferenceNet task, with the events DSH records and what the InferenceNet profile does at each point.

  1. 01

    Claim the input and assemble the prompt

    session/prompt puts the task request into the agent’s durable inbox and wakes the loop. The loop opens the turn, claims the pending input and asks ctx.systemPrompt to assemble the prompt sections and tool schemas through the system-prompt/assemble waterfall.

    Events
    agent/inbox/spliced · turn/start
    InferenceNet system prompt
    persona only
  2. 02

    Decide whether to take the step

    agent/pre-step is a waterfall over the claimed messages. A listener can rewrite them, add context, or reject the step, which closes the turn as blocked. In dsh-base, compaction listens here and summarizes old history once it reaches 80% of the context window.

    The InferenceNet profile mounts no pre-step listener, so the task request enters unchanged and the history is never compacted.

  3. 03

    Prepare the call, then write it down

    agent/request lets listeners change the provider, model or limits; ctx.llm.prepareCall then binds one adapter route. Only after both succeed does the loop append system/message, the accepted user/message and request/header. The request itself is derived from the log and frozen.

    Anything the model sees has a session event behind it, so the log can rebuild every request the loop sent.

    Events
    step/start · system/message · user/message · request/header
  4. 04

    Stream one model call

    The frozen request passes through the llm/stream waterfall to the adapter. In InferenceNet the llm-pi-ai route sends it to the loopback bridge. The bridge checks the budget, forwards a non-streaming request upstream with the remaining token allowance, records the raw response and usage, and answers DSH in SSE form.

    Budget check
    before every call, at the bridge
    Retries
    0 in DSH and in the bridge
  5. 05

    Record the answer

    A finished call becomes one assistant/message holding its timed stream and usage. A failed call becomes assistant/attempt and enters the agent/request-error waterfall, where llm-retry or compaction may retry inside the same step; a cancelled call ends the turn as aborted. A call that hits its token limit drops its tool calls and ends the turn as max-tokens.

    InferenceNet sets maxRetries to 0, and its bridge refuses cut-off replies. A cut-off reply, an exhausted model budget or an upstream error reply therefore ends the turn with an error, and the attempt fails. The exceptions are a 401, 403, 429 or redirect reply, a transport error and a reply without usage: the bridge then marks the attempt uncertain and stops the whole study.

  6. 06

    Run the tool calls

    Each call is logged as tool/call, then passes tools/pre-execute, tools/execute and tools/post-execute before its tool/result is committed in model order. Calls that declare themselves safe to run concurrently share a pool of up to ten; every other call runs alone.

    run_python
    exclusive · no DSH deadline
    Container
    fresh · no network · 6 GB · 2 CPUs · ≤90 s
  7. 07

    Close the step, or the turn

    step/end is always written. If tool results owe the model another request, the next step starts from the claim. Otherwise agent/turn-stopping lets listeners steer once more, and turn/end records why the turn closed: completed, max-tokens, blocked, aborted or error.

    InferenceNet requires
    turn/end completed
    Loop limit
    none in DSH · bridge budgets
  8. 08

    Hand back the final program

    The SDK waits for session.status idle, then returns the text of the last assistant/message and the turn/end reason. The controller takes exactly one fenced Python program from that text, replays it in a fresh container and scores it privately. Programs tried earlier with run_python are never used as the answer.

    Final program
    last root assistant/message
    Scoring
    local-paper-v1 · controller only

Same tasks, two configured harnesses

Before comparing results

This page reports no DSH scores. The migration commit was checked offline and with synthetic runs. The DeepSeek Harness entry on the Hugging Face leaderboard came from a separate controller, with a bwrap sandbox and 1,800 s per attempt, whose source has not been matched to this branch; it does not measure the wiring shown here. The ModularRSI run on the Evolution page used its own DeepAgents settings, with 12 model calls, 8 run_python calls, 1,800 s and streaming Chat, so its numbers are not a baseline for the limits above.

A loop-only comparison would first give both arms the same tools and prompt. That control does not exist yet.
