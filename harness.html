Harness

What turns a model into an agent.

A harness is the software that runs a language model as an agent. This page draws the line between the model, the harness, the agent, the SDK that drives it, the environment it acts on and the evaluator that scores it; lists 57 entries from the harness ecosystem in October 2026; and takes three apart in one template, so that the differences between DeepAgents, Superpowers and DeepSeek Harness line up. It ends with how self-evolution methods relate to a running harness.

01 / Definition

What a harness is

A harness is the software that runs a language model as an agent: it decides what the model sees at each step, carries out the tool calls the model makes, returns the results, keeps the state of the run and decides when the run stops.

A model takes text in and returns text. Anthropic defines an agent harness as “the system that enables a model to act as an agent” and adds that evaluating an agent means “evaluating the harness and the model working together”. LangChain puts the relationship as “Agent = Model + Harness”. The same model can score differently in a different harness, so a result belongs to the pair. Evaluation papers often call the same layer a scaffold.

The leaderboard follows this split. A Model row is a single call with no agent loop: one code-generation call, after which InferenceNet executes the returned program. A Model + Harness row runs the model inside a named harness: the harness passes the model’s code to the run_python tool that the evaluation supplies and returns the tool’s feedback to the model before it submits a final program. The tasks, data, sandbox, budget and scorer belong to the evaluation, not to the harness.

Eight things every harness decides

  • Runs on

    Where the harness runs and how it is driven: a library in the caller’s process, a separate CLI or server process, or a hosted service, and how it reaches models.

  • Execution loop

    The control flow of a run: call the model, turn its reply into actions, run them, add the results and repeat, with hooks or events between the phases.

    • step
    • hooks or events
    • parallel calls

  • Tools

    The actions the model can request and how each is carried out: the tool list and descriptions, the executor behind each tool and the result returned to the model.

    • built-in tools
    • MCP
    • executor
    • result format

  • Context and memory

    What the model sees on each call and what is kept: system prompt, instruction files, the running history and its compaction, large results moved aside, and anything carried across runs.

    • compaction
    • session log

  • Delegation

    Whether and how work is handed to other agents: subagents with their own context, parallel workers, and how their results come back to the main run.

  • Stopping and recovery

    • resume

DeepAgents 0.7.13 Library harness

Middleware around a LangGraph loop

DeepAgents is a Python library built on LangChain. Its main function, create_deep_agent(), takes LangChain’s standard agent loop (create_agent) and adds middleware, code that runs around every model and tool call, plus file tools, helper agents called subagents and a place to keep files. The result is a LangGraph graph that runs inside the caller’s own Python program. Most of what it adds keeps the model’s input within its context window.

In 0.7.23, SkillsMiddleware moves to just before prompt caching and UnsupportedContentMiddleware is added after HumanInTheLoopMiddleware.

  • Since 0.7.0 DeepAgents ships no base prompt of its own, and planning is opt-in: write_todos is not in the default stack. The tools’ own descriptions carry the usage guidance.
  • Built-in harness profiles apply automatically to some Anthropic, OpenAI Codex and NVIDIA Nemotron models and add model-specific prompt text; the Codex profile also adds write_todos.
  • The default general-purpose subagent gets the caller’s tools and the file tools but no task tool, so it cannot delegate further. Turning it off takes a harness profile; with no synchronous subagent left, the task tool disappears.
  • LangGraph runs the agent in supersteps: in each round every node with pending input runs, and the tools node runs once for each tool call; a model call and the tool calls that follow it take at least two rounds. The limit of 9,999 supersteps comes from LangChain’s create_agent and DeepAgents sets it again, so it does not count model calls, and a run has no limit on model calls or tokens unless the caller adds one.
  • LocalShellBackend runs execute on the host with no process isolation or resource limits; its documentation recommends human approval, or a sandbox backend for untrusted code.
One task, step by step
  1. 01

    Assemble the agent once

    create_deep_agent() resolves the model and its harness profile, builds the middleware stack, the general-purpose subagent and the tool list, and hands them to LangChain’s create_agent, which compiles a LangGraph graph.

    Default backend
    StateBackend, files in graph state
    Recursion limit
    9,999
  2. 02

    Enter the graph

    invoke() starts the graph and runs the before_agent hooks once. In the default stack only PatchToolCallsMiddleware has one: it answers any earlier tool call that never got a result. Skills and memory, when configured, load their files here.

    Default before_agent
    PatchToolCallsMiddleware
  3. 03

    Shape the request

    The model node builds a request from the model, the tools, the system message and the history, and passes it through the wrap_model_call chain, outermost first. File tools the backend cannot serve are dropped, history past the threshold is summarized and cache markers are added.

    Summary trigger
    85% of the input window, else 170,000 tokens
  4. 04

    Call the model

    The innermost handler binds the tools and calls the chat model with the system message followed by the history; one AI message comes back. If the provider rejects the request as too long, the history is summarized and the call is made again.

    Model input
    system message, then the history
  5. 05

    Route on the reply

    after_model hooks run; the default stack has none, while human-in-the-loop adds one that can pause for approval. A reply without tool calls leaves the loop; otherwise each tool call goes to the tools node as its own task.

    No tool calls
    leave the loop
  6. 06

    Run the tool calls

    Each call passes the wrap_tool_call chain and runs as a task in the same superstep, so the calls of one reply run concurrently. Oversized results move into backend files; task runs a subagent and returns its last message. The results go back to the model node.

    Result offload
    over 20,000 tokens
  7. 07

    End the run

    When the model replies without tool calls, any after_agent hooks run and the graph ends; invoke() returns the final state, whose last AI message is the answer. Passing the recursion limit raises an error. Within a run, state passes from one superstep to the next as usual; a checkpointer, if one is passed, saves a checkpoint after each superstep so the run can be resumed later.

    Answer
    the last AI message
    Checkpointer
    none unless passed

Superpowers 7.0.0 Extension

Skills that steer a host agent

Superpowers adds no loop or tools of its own, and no process beyond an optional local server for brainstorming mockups. It is a plugin of 15 skills plus a small adapter for each host: a bootstrap at session start tells the model to use the skills, and the skills impose a workflow of brainstorming, planning, test-driven work by subagents, review and a person’s decision at the end. Its maker calls it a software development methodology for coding agents.

One task, step by step
  1. 01

    The bootstrap loads

    When a Claude Code session starts, is cleared or is compacted, the plugin’s hook returns the whole using-superpowers skill as added context, and the host lists the other skills by name and, within its listing budget, by description. From then on the model is told to invoke any skill that might apply before it replies or acts.

    Hook events
    startup, clear, compact
    Injected
    about 3,400 characters
  2. 02

    A build request triggers brainstorming

    A request to build something new matches brainstorming’s description, so the model loads that skill before writing any code. It asks one open question per message and plays back each part it understood for correction.

    Questions
    one per message
  3. 03

    Size the work, approve a design

    The agent names a size: a quick task, a small change agreed in chat, or a project with a design document. A fresh subagent reads the design as its builder would, the agent brings back only the questions that change what gets built, and nothing is built until the person approves.

    Design
    docs/superpowers/specs/
    Gate
    approval before any building
  4. 04

    Write the plan, choose an executor

    writing-plans saves a plan whose tasks give files, interfaces, test assertions and commands. The person reviews it and picks subagent-driven or native execution; the agent recommends one with a reason drawn from the plan.

    Plan
    docs/superpowers/plans/
  5. 05

    Isolate the work, open a ledger

    At execution the agent checks whether it already sits in a worktree, asks before creating one, installs dependencies and runs the baseline tests. It opens a git-ignored workspace for the plan with a ledger that records progress, so a session that loses context can resume from the file.

    Workspace
    .superpowers/sdd/<plan>/
  6. 06

    Implement and review each task

    For each task the coordinating session writes a brief and dispatches a fresh implementer on a named model, which follows TDD, commits and writes a report. A read-only reviewer gets the brief, the report and the diff; findings go through up to five fix rounds before the ledger marks the task complete.

    Fix rounds
    1–3 resume; 4–5 fresh, stronger model
  7. 07

    Review the whole branch once

    After the last task one reviewer on the most capable model reviews the branch from its merge base. Findings get one fix wave, and the final message lists every decision the agent made on its own under “Rulings I made”.

    Fix waves
    one
  8. 08

    Test, then the person integrates

    finishing-a-development-branch runs the full test suite, confirms the base branch and offers three choices: merge locally, push and open a pull request, or keep the branch. It removes only worktrees it created and discards work only on an explicit, typed request.

    Menu
    merge, PR or keep

In InferenceNet. InferenceNet does not run Superpowers. Its default workflow waits for a person at the design approval, the plan review and the finishing menu, which an unattended benchmark run would have to answer or bypass.

DeepSeek Harness 0.1.5-rc.1 Product harness

Plugins around a session log

DeepSeek Harness is built on Cordis, a plugin framework: every part of it, even the agent loop, is a plugin that can be swapped from configuration. A profile picks the plugins by stacking bundles (prepared lists of plugins) and patch files. Everything the model sees is first written to a session log that is only ever appended to. Applications start it as a separate program: a web UI, a desktop app, a one-shot command or a server that the SDKs talk to.

  • DeepSeek Harness is a developer preview. Its README warns of compatibility-breaking changes, every GitHub release so far is a prerelease, and its safety notes say it has not had a security audit and that sandboxing and approvals reduce risk without guaranteeing isolation.
  • The agent loop has no step, turn or recursion budget. Its README leaves bounding runaway turns to an extension point such as agent/turn-stopping, so deployments enforce budgets outside the loop.
  • In the stock sdk profile, actions that need approval are refused: dsh-base sets the approval policy to ask, but the 0.1.5-rc.1 SDK protocol has no way to ask the caller. This is read from code, not observed in a run.
  • Master (0.2.1-alpha.2, 9 Oct 2026) adds a developer message event and a tool role, moves sessions to format v4, grows dsh-base to 94 rows and moves the ralph tool into an opt-in experimental bundle.
One task, step by step
  1. 01

    Launch dsh with a profile

    The Python SDK starts the runtime wheel’s dsh binary with the sdk profile and an explicit home directory. The launcher applies dsh-base, dsh-sdk-app and any patch files to an empty tree and mounts the resulting plugins.

    Profile sdk
    86 rows
    Transport
    JSON-RPC 2.0 on stdio
  2. 02

    Initialize the model route

    initialize sends the working directory, provider, model and optional reasoning effort. The provider needs an adapter, which dsh-base supplies for the DeepSeek API, so a missing adapter, unknown model or unsupported effort fails before any prompt runs.

    Python SDK default
    deepseek-official / deepseek-v4-flash
  3. 03

    Queue the prompt, open a turn

    session/prompt creates the session’s agent on first use and puts the message in the agent’s durable inbox. The loop writes turn/start and claims the queued input.

    Logged
    agent/inbox/spliced, turn/start
  4. 04

    Assemble the prompt, then pre-step

    DeepSeek Harness assembles the request: the system prompt from its sections, plus the schemas of the tools the model may call; if the runtime context has changed, a snapshot of it is added as a user message. Plugins listening on agent/pre-step then run in turn (a waterfall) and can accept, rewrite or reject the queued messages; compaction and AGENTS.md loading happen here.

    Rejected
    turn/end blocked, no step
    Compaction
    at 80% of the window
  5. 05

    Prepare, log and stream one call

    After step/start, plugins on agent/request choose the model route for this call; only then are the system message, the user messages and the request header written to the log. The request is then rebuilt from the log and made immutable, so the model sees exactly what was logged, and the reply streams back. A finished call is logged as assistant/message; a failed one as assistant/attempt, and it may be retried.

    Rule
    model-visible means logged
    Retries
    up to 5 per step
  6. 06

    Run the requested tools

    Each tool call is logged, then passes tools/pre-execute (allow, deny or ask), the registered guards, tools/execute around the tool body and tools/post-execute; its result is committed in model order. Concurrency-safe tools share a pool of up to 10; every other call runs alone.

    Large results
    over 50,000 bytes saved to a file
  7. 07

    Close the step, or the turn

    step/end is always written. If tool results owe the model another request, or new input arrived, the next step starts; otherwise agent/turn-stopping lets listeners steer once more before turn/end records why the turn closed.

    turn/end in a live run
    completed, max-tokens, blocked, aborted or error
    Loop limit
    none
  8. 08

    Return the result, keep the log

    The SDK waits for the session to go idle and returns the last assistant text and the turn/end reason. The session stays in the home directory as JSONL, so the same session id can continue later.

    Storage
    session.v3.jsonl, zstd by default

05 / Self-evolution

Running a harness, and changing it

Running a harness and optimizing it are two different layers. The execution loop runs the current configuration: it builds the context, calls the model and runs tools. That configuration is not always frozen during a task: Cordis registrations are reversible and the DeepSeek Harness web profile reloads its patch files live, and Superpowers’ writing-skills skill has the agent write new skills. Self-evolution is a different loop: it proposes harness versions from feedback, tests them and keeps candidates by a rule that differs between methods. The three methods below run that loop mostly offline, between runs; using a harness does not by itself optimize it.

Three published methods run such an optimization loop: ModularRSI (Wu et al., 2026), Self-Harness (Zhang et al., 2026) and Meta-Harness (Lee et al., 2026). What each one edits, who proposes the edits and how candidates are tested and kept are compared on the Self-evolving page, together with InferenceNet’s own development study.
