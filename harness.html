Challenge harnesses

Designing harnesses for the two challenges

InferenceNet Challenge invites participants to build agents for empirical research and business analysis. A harness organizes context, tool execution, state and verification around a model. Our current multi-harness comparisons and self-evolution experiments were completed in Phase 1 on econometric replication; extending harness adaptation to the finance and HR workflow on Harbor and Claude Code is the next stage.

  • 01 · Context and information

    What enters each step

    Arrange how task requirements, domain rules and source materials enter the context, and preserve key findings, intermediate progress and unresolved questions across long runs.

  • 02 · Tools and actions

    How the agent acts on data and files

    Provide clear operations for inspecting datasets, running statistical or financial scripts, and generating documents or workbooks, returning structured execution output to the model.

  • 03 · Checks and recovery

    How errors and gaps become feedback

    Turn runtime errors, statistical diagnostics and file readbacks into evidence for the next decision so the model can revise its analysis or deliverables before stopping.

  • 04 · Resources and delivery

    How limits and final outputs are enforced

    Manage permissions, call caps, token budgets and sandbox timeouts, and check that required outputs exist, retain required formulas or code, and follow the submission format.

01 / Definition

What a harness is

A harness is the software that runs a language model as an agent: it decides what the model sees at each step, carries out the tool calls the model makes, returns the results, keeps the state of the run and decides when the run stops.

Next: harness systems →

Definition details: terms, responsibilities and boundaries

A model takes text in and returns text. Anthropic defines an agent harness as “the system that enables a model to act as an agent” and adds that evaluating an agent means “evaluating the harness and the model working together”. LangChain puts the relationship as “Agent = Model + Harness”. The same model can score differently in a different harness, so a result belongs to the pair. Evaluation papers often call the same layer a scaffold.

The 1,000-task Selected_1000 board follows this split. A Model row is a single call with no agent loop: one code-generation call, after which InferenceNet executes the returned program. A Model + Harness row runs the model inside a named harness: the harness passes the model’s code to the run_python tool that the evaluation supplies and returns the tool’s feedback to the model before it submits a final program. The tasks, data, sandbox, budget and scorer belong to the evaluation, not to the harness. The Dev100 v10 development board has no Model rows: it runs 14 models in four harness configurations (section 06).

    • step
    • hooks or events
    • parallel calls

  • Tools

    The actions the model can request and how each is carried out: the tool list and descriptions, the executor behind each tool and the result returned to the model.

    • MCP
    • executor

  • Context and memory

    What the model sees on each call and what is kept: system prompt, instruction files, the running history and its compaction, large results moved aside, and anything carried across runs.

    • AGENTS.md
    • compaction
    • session log

  • Delegation

    Whether and how work is handed to other agents: subagents with their own context, parallel workers, and how their results come back to the main run.

    • depth limit

  • Stopping and recovery

    When a run ends and how it survives failures: a reply without tool calls, a limit or a rejected step; retries, summarizing on overflow, resuming an interrupted run.

    • step limit
    • retries
    • resume

  • Permissions and limits

    Controls that hold whether or not the model cooperates: which tools may run and which need approval, sandbox and file permissions, and turn or spend limits inside the harness.

    • permissions
    • approval
    • sandbox
    • budgets

  • Extension points

    How behavior is added or replaced without changing the harness’s own code: middleware or hooks, plugins, skills, MCP servers, custom tools and configuration profiles.

02.4 / Unified evaluation

Integrating diverse harnesses into a unified evaluation system via Harbor

Harnesses differ widely in how they are packaged: some are Python libraries (DeepAgents, OpenAI Agents SDK), some are standalone CLI binaries or JSON-RPC servers (Claude Code, DeepSeek Harness, Codex CLI, OpenCode), and others are minimal reference loops (Terminus-2, mini-SWE-agent). The Harbor evaluation framework unifies them behind a single task-and-container contract so every Model + Harness pair faces the same environment, budgets and independent verifier.

  • 01 · Standardized task bundle

    One task format across domains

    Packages the prompt, input datasets or business documents, environment image and resource limits while keeping reference values and grading rubrics outside the container.

  • 02 · Pluggable agent adapter

    Mount CLI, SDK or library harnesses

    Wraps standalone CLI agents (Claude Code, Codex, OpenCode), JSON-RPC processes (DeepSeek Harness) and Python graph libraries (DeepAgents) behind a uniform run interface and model-routing proxy.

  • 03 · Isolated execution & hooks

    Reproducible sandboxes and pre-submit checks

    Executes every tool call in an isolated container and records full JSONL trajectories, making it straightforward to inject statistical diagnostics or Word/Excel readback hooks before submission.

  • 04 · Out-of-loop verification

    Independent replay and rubric scoring

    Grades the submitted Python program or business deliverables in a clean verification pass after the agent terminates, separating execution errors and verifier errors from task scores.

03 / Breakdown

Anatomy of a harness: DeepAgents 0.7.13

To see how a harness works on the inside, we break down DeepAgents (LangChain’s library harness, pinned at 0.7.13 in InferenceNet Phase 1) across the eight core responsibilities: its three-layer LangGraph architecture, its middleware stack, one complete run from start to finish, and how InferenceNet wires and evolves it.

DeepAgents 0.7.13 Library harness

Middleware around a LangGraph loop

DeepAgents is a Python library built on LangChain. Its main function, create_deep_agent(), takes LangChain’s standard agent loop (create_agent) and adds middleware, code that runs around every model and tool call, plus file tools, helper agents called subagents and a place to keep files. The result is a LangGraph graph that runs inside the caller’s own Python program. Most of what it adds keeps the model’s input within its context window.

One task, step by step
  1. 01

    Assemble the agent once

    create_deep_agent() resolves the model and its harness profile, builds the middleware stack, the general-purpose subagent and the tool list, and hands them to LangChain’s create_agent, which compiles a LangGraph graph.

    Default backend
    StateBackend, files in graph state
    Recursion limit
    9,999
  2. 02

    Enter the graph

    invoke() starts the graph and runs the before_agent hooks once. In the default stack only PatchToolCallsMiddleware has one: it answers any earlier tool call that never got a result. Skills and memory, when configured, load their files here.

    Default before_agent
    PatchToolCallsMiddleware
  3. 03

    Shape the request

    The model node builds a request from the model, the tools, the system message and the history, and passes it through the wrap_model_call chain, outermost first. File tools the backend cannot serve are dropped, history past the threshold is summarized and cache markers are added.

    Summary trigger
    85% of the input window, else 170,000 tokens
  4. 04

    Call the model

    The innermost handler binds the tools and calls the chat model with the system message followed by the history; one AI message comes back. If the provider rejects the request as too long, the history is summarized and the call is made again.

    Model input
    system message, then the history
  5. 05

    Route on the reply

    after_model hooks run; the default stack has none, while human-in-the-loop adds one that can pause for approval. A reply without tool calls leaves the loop; otherwise each tool call goes to the tools node as its own task.

    No tool calls
    leave the loop
  6. 06

    Run the tool calls

    Each call passes the wrap_tool_call chain and runs as a task in the same superstep, so the calls of one reply run concurrently. Oversized results move into backend files; task runs a subagent and returns its last message. The results go back to the model node.

    Result offload
    over 20,000 tokens
  7. 07

    End the run

    When the model replies without tool calls, any after_agent hooks run and the graph ends; invoke() returns the final state, whose last AI message is the answer. Passing the recursion limit raises an error. Within a run, state passes from one superstep to the next as usual; a checkpointer, if one is passed, saves a checkpoint after each superstep so the run can be resumed later.

    Answer
    the last AI message
    Checkpointer
    none unless passed

05 / Self-evolution

From running a harness to evolving it

An execution loop runs a fixed harness configuration on a task; an optimization loop sits outside execution, inspects trajectories and failure modes across tasks, proposes targeted edits to the harness (prompts, tool descriptions, observation formatting, middleware hooks or code), and retains only non-regressive improvements under a fixed evaluator.

The Self-evolving page presents the two-layer execution-and-optimization diagram, compares recent offline and online self-evolution methods (ModularRSI, Self-Harness, Meta-Harness, AHE, RHO, Harness-R1, RRSI and WHALE), and documents InferenceNet’s Phase 1 ModularRSI evolution study alongside our Phase 2 roadmap for Harbor and Claude Code.
