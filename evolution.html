Phase 2 · Harness self-evolution

The harness rewrites itself from its own trajectories.

Phase 1 placed models inside DeepAgents and measured what the harness adds. Phase 2 keeps the model and DeepAgents fixed. Five small harness functions around them are rewritten by a ModularRSI-style evolution loop that reads InferenceNet trajectories. This page follows the first complete run.

01 / Design

Five editable functions around a fixed core

ModularRSI splits an agent harness into five modules and evolves each one separately. We apply the idea to DeepAgents without changing the SDK. Each module is one Python function that the harness calls at a fixed point in the loop. All five start as no-ops, so the initial harness behaves exactly like the phase 1 DeepAgents configuration.

The five evolvable functions and where the harness calls them

agent_loopWhen to stop exploring and ask for the final program, and when to ask for a repairBefore every model call(remaining_model_calls, last_tool_failed) → {force_final, repair_nudge}

02 / Evolution loop

How one evolution run works, step by step

Five module lineages start from the same no-op source and the same initial trajectories. Each lineage may change only its own function. The loop below ran three epochs, then combined the accepted functions into one frozen harness.

  1. 01

    Split the tasks before anything runs

    From the 1,000 Selected_1000 tasks, 100 become the development set and 900 are held out. Tasks from the same paper or with identical input files stay on the same side. The evolution loop never dispatches the 900 held-out tasks.

    Development tasks
    100
    Held-out tasks
    900 · not run yet
  2. 02

    Roll out every harness version

    Each harness version solves every development task three times with DeepSeek V4 Pro inside DeepAgents. Every run_python call starts a fresh sandbox; nothing persists between calls.

    Rollouts per evaluation
    300
    Budget per rollout
    12 model calls · 8 tool calls
    Output and time limit
    32,768 tokens · 30 min
    Sandbox per call
    6 GB · 2 CPUs · 90 s
  3. 03

    Score in private

    The evaluator reruns each final program from scratch and compares its output with the hidden reference. The model, the analyst and the editor never see reference values or scorer internals.

  4. 04

    Diagnose by contrast

    Tasks are grouped by outcome across their three rollouts. An analyst model compares successful and failed rollouts of the same task, reads all 100 tasks in batches of up to ten, and names recurring problems. A problem is kept only when at least two different tasks support it.

    Comparing the same task removes most task difficulty from the comparison, so the remaining difference points at the harness.

  5. 05

    Edit one function

    For each lineage, an editor model sees only its function, the history of accepted versions and the aggregated finding. It returns a new version of that function. Static checks verify syntax, imports, the interface and the editing scope.

  6. 06

    Review the diff, then probe on real tasks

    A reviewer model rejects changes that encode task-specific details. The candidate then runs two real development tasks. If the probe completes without protocol or runtime errors, the candidate is promoted.

    Promotion does not look at development scores. The scores in section 03 are recorded for analysis only, so an accepted version can score lower than its parent.

  7. 07

    Repeat for three epochs

    Each module gets at most one edit per epoch. A promoted version becomes the parent for the next epoch, and every promoted version receives a full 300-rollout evaluation.

    Candidate slots
    15
    Promoted
    8
    Rejected by diff review
    3
    Editor output or edit invalid
    4
  8. 08

    Integrate, refine once, freeze

    The accepted versions of agent_loop, completion and tool_use are combined and probed together. One integration epoch reads the combined trajectories and makes a single checked refinement. The result is frozen by hash before any held-out evaluation.

    Changed modules
    3 of 5
    Frozen source
    17f138b9

04 / What improved

Fewer runs end without a final program

Comparing the initial and frozen harness on the same 100 development tasks, with three rollouts each, the clearest change is in how runs end. Far fewer rollouts finish with tool calls and no final program, and more rollouts produce a result the evaluator can score.

How to read these numbers

Most of the gain comes from more rollouts finishing with a program the evaluator can score: 171 → 217 of 300. Among scored rollouts, the full-replication share fell from 47.4% to 41.9%. The evolved harness mainly fixed how runs end; it did not make the statistics more precise.

These are development-set results. The same 100 tasks were used to diagnose problems, each harness version was evaluated once with three rollouts per task, and no confidence intervals are reported. The frozen harness has not yet run on the 900 held-out tasks. These results are not part of the leaderboard.

05 / Evolved code

What the frozen functions say

All five functions started as no-ops: tool_use and completion returned an empty string, agent_loop never intervened. Below are the three functions that changed, exactly as frozen. observation and context are unchanged.

tool_use.py · 3 epochs + 1 refinement
"""Model-visible Python-tool guidance hook."""


def tool_use() -> str:
    """Return additional general tool-use guidance, if any."""
    return (
        "Use tool calls efficiently. Prefer combined or batched operations, inspect data "
        "shape and dtypes in few calls, and verify final programs with targeted unit tests "
        "rather than repeated exploratory calls. Plan a multi-phase call budget before starting: "
        "allocate a bounded number of calls for initial data inspection, one consolidated call "
        "for exploratory diagnostics or transformations, and always reserve at least two calls "
        "for executing and validating the final program. Never spend exploratory calls on "
        "information you can derive from existing outputs or task context. If a call budget is "
        "available, reserve enough calls for final verification. When a tool call returns only a "
        "signature echo, runtime warning, empty result, or indicates an unavailable tool or file, "
        "do not retry the same call or rely on it for critical specification details. Instead, "
        "reason from information already present in existing outputs, task description, or any "
        "attached artifacts, and proceed with the most direct, defensible next step. When "
        "filesystem inspection is unavailable, prefer direct artifact-independent implementation "
        "and inference from available context to avoid stalled exploration. Before making a final "
        "submission, execute the full solution program at least once and verify it completes "
        "without error, rather than submitting unexecuted code or prose."
    )
completion.py · 3 epochs
"""Final-answer guidance hook."""


def completion(remaining_model_calls: int) -> str:
    """Return a bounded reminder about complete program submission, if any."""
    if remaining_model_calls > 1:
        return (
            "If you have verified your complete program, submit it now. "
            "If you have not yet verified it and still have tool or execution attempts available, "
            "continue debugging instead of submitting an unverified program. "
            "After any tool call or execution attempt, always finish your turn with an assistant "
            "message summarizing the result before waiting for another step."
        )
    if remaining_model_calls == 1:
        return (
            "You have one model call remaining. Use it to submit your complete program only if it is "
            "already verified. If it is not verified, you may still use remaining tool or execution "
            "attempts to debug before your final submission. End every turn with a final assistant "
            "completion after tool calls so your verified result is captured by the harness."
        )
    return (
        "Submit your complete program now. End this turn with a final assistant completion so "
        "the submitted program is recorded as your final answer."
    )
agent_loop.py · 2 accepted epochs
"""Agent-loop decision hook; edited versions must retain this interface."""


def agent_loop(remaining_model_calls: int, last_tool_failed: bool) -> dict[str, bool]:
    """Return final-only and repair decisions for the next model request.

    Budget-conscious scheduling: when the model can no longer afford a
    meaningful followup cycle, the loop stops issuing exploratory calls and
    asks for a final result.  A recent tool failure only triggers a repair
    nudge while there is enough budget remaining to act on it.

    Repeated tool failures are treated as a stronger signal that the current
    computation path is unproductive.  This prevents the loop from burning the
    remaining budget on redundant retries; instead it forces finalization so
    the model must consolidate whatever partial or negative result it has
    accumulated before tool-call exhaustion.
    """
    can_afford_followup = remaining_model_calls > 1

    # With only one call left there is no room for a repair plus a final
    # answer, so finalization is forced regardless of tool state.
    if not can_afford_followup:
        return {"force_final": True, "repair_nudge": False}

    # With two calls remaining, a repair nudge is only useful if the model
    # has not already consumed the budget on failed repair attempts.  In that
    # case the loop should stop nudging and force a final consolidation.
    if last_tool_failed and remaining_model_calls <= 2:
        return {"force_final": True, "repair_nudge": False}

    # Otherwise the failure can still be repaired while preserving a final call.
    force_final = False
    repair_nudge = last_tool_failed and can_afford_followup

    return {"force_final": force_final, "repair_nudge": repair_nudge}

Full replication requires the coefficient and standard error within 1% relative error and the p-value within 0.01 absolute error (local-paper-v1). The 5% measure requires both the coefficient and the standard error within 5%. This differs from the leaderboard’s partial replication, which checks the coefficient only.

Method: ModularRSI by Wu et al., 2026. This adaptation keeps the five-module split, contrastive trajectory diagnosis, scoped edits, diff review, execution probes and integration. It edits one entry function per module rather than a library of variants, and it does not implement task-aware function composition.
