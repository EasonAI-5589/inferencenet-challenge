01 / Concept

What self-evolution changes, and what it leaves alone

Harness self-evolution, also called automatic harness optimization, means proposing, testing and keeping harness versions on the basis of feedback from the harness’s own runs. The three methods detailed on this page do this in offline rounds: an outer loop edits the harness between evaluations, and the model’s weights do not change. That is how these three work, not a limit of the idea. Other methods change the harness across a stream of tasks, during a single run or for each task instance, and some also train the weights; the research map below places them.

  • Fixed

    Model

    The language model and its weights. Within a controlled harness comparison, both versions use the same solving model. Separate searches may use different frozen solving or proposer models, and must be identified separately. Methods that train model weights are another branch on the research map.

  • Edited

    Harness

    The software that runs the model as an agent: the loop, tool definitions, how observations are shown, how context is kept, prompts, memory and when to stop. This is what the loop changes, as a whole or in parts.

  • Observed

    Agent

    The model running inside one harness version on one task. Its trajectories and outcomes are the evidence the loop learns from.

  • Version-dependent

    SDK

    The libraries that implement the agent runtime. Our v1 keeps DeepAgents unchanged and edits added hooks. Our v2 uses a pinned copy of DeepAgents, LangChain and LangGraph with scoped source edits. Model weights and the evaluator remain fixed in both versions.

  • Fixed

    Environment

    What the tools act on: tasks, data, files, sandboxes. It is held constant so that a change in score can be traced to the harness.

  • Fixed

    Evaluator

    The scorer that grades finished runs. It decides which version looks better, so it is never among the things edited; methods differ in how much of its output the proposer may see.

The editable boundary must be recorded per method and release. In particular, the unchanged SDK in the historical v1 study is not a restriction on v2. All results below retain their original version, task split and selection policy.

The six terms follow the Harness page, which also explains how harnesses such as DeepAgents and DeepSeek Harness, and extensions such as Superpowers, are built. This page is about improving a harness once it exists.

Research map · 2025–2026

When the harness changes, and what decides

Methods in the four lanes below run an agent, read feedback from those runs, edit part of the harness and keep some of the edits. They differ in when that happens: between rounds on a task set, across a stream of new tasks, within one continuing run, or once per task instance. The lanes are alternatives, not stages of a history. Around them sit routes that change or describe something else: a branch that also trains model weights, systems that compose several harnessed agents, the representation a harness is written in, and the evaluation that scores it.

02 / Improvement loop

One loop behind all three methods

The methods differ in how much of the harness they open up, who writes a change and how a candidate is judged. Each iteration still has the same five steps, and the candidates evaluated so far, with their run evidence, inform the proposals of the next round.

In these three methods the search runs offline

In all three methods, versions are proposed and selected between evaluation rounds, and the result is frozen before it is evaluated or used. When an evaluation feeds tasks as a stream, as in Meta-Harness’s online text-classification setting, that describes how the application receives its inputs. It does not mean the harness edits itself while it runs.

Two methods on the research map differ on exactly this point: Evo-Harness updates its harness between the tasks of a stream, and Continual Harness edits it during a single run.

Six questions to ask of any method

  1. Which part of the harness may change?
  2. Who proposes the change?
  3. Which trajectories and feedback does the proposer see?
  4. How is a candidate accepted, merged or rejected?
  5. When does the search run, and is the result frozen before use?
  6. What stays fixed: model, environment, evaluator, tasks?

03 / Methods

Three offline methods in detail

ModularRSI, Self-Harness and Meta-Harness come from different groups and are separate methods. Each mechanism summary follows the paper’s description; the official repositories are listed separately in section 06, and their released code may differ from what the papers describe. The steps describe one iteration of the method’s loop. Reported results are the authors’ and have not been reproduced here. Notes headed “How to read it” are our interpretation, not the authors’ wording.

Method 1

ModularRSI

ModularRSI: Modular and Generalizable Recursive Harness Self-Improvement

  • Wu et al. · arXiv 2609.14857 v1 · 14 Sep 2026
  • Code: IQuestLab/ModularRSI at b5c72c3

Evolves a Terminus-2-based harness one module at a time. The agent’s own model contrasts passing and failing rollouts of the same task on evolution tasks curated apart from the evaluation benchmarks, then changes functions inside one of five modules: agent loop, tool use, observation management, context management and task completion detection. The evolved modules are integrated and frozen before any benchmark evaluation.

How to read itThe execution check runs a candidate on two tasks sampled from the current batch to show that it runs without runtime or protocol errors. It is not a statistical test that performance did not drop.

How to read itA task-aware composer, which also runs during evolution, picks functions for each task. At evaluation time it chooses only among the frozen functions; the harness is not edited while it runs.

One iteration

  1. Roll out on evolution tasks

    Run the current harness K times on each task of a batch of evolution tasks. The paper curates 2,000 executable evolution tasks that do not overlap with the evaluation benchmarks and uses 240 of them in its main experiments. Each task’s own tests mark every rollout as passed or failed.

    Paper §3.3, §5.3

  2. Sort tasks by outcome

    Tasks with mixed results pair a passing with a failing rollout. Tasks that always fail look up an earlier success in a trajectory memory, or are diagnosed on their own. Tasks that always pass are checked for wasted steps.

    Paper §3.3, Eq. 1

  3. Diagnose against one module

    The Code-Modify Agent, run by the same model, reads the trajectories, finds where the passing and failing rollouts diverge and asks whether a change to the module under evolution would have changed the outcome.

    Paper §3.3; App. B, C.1

  4. Rank candidate changes

    Findings that target the same function are merged into one candidate, whose vote count is the number of distinct tasks supporting it. An evolution history of earlier changes helps avoid repeated or contradictory edits.

    Paper §3.4

  5. Write one scoped change

    The agent writes one change that has to hold for all supporting findings, by adding, modifying or replacing a function variant, and it may write only inside that module.

    Paper §3.4; App. C.2

  6. Pass three gates or roll back

    A program check of syntax, imports and protocol; a diff review that does not see rewards and rejects task-specific code; an execution check on two tasks sampled from the current batch. A change that fails any gate is rolled back, and one that passes becomes the next generation.

    Paper §3.5; App. C.3

  7. Integrate and freeze

    After three epochs per module, the five modules are combined and one integration epoch repairs cross-module conflicts; then the function library is frozen. Overlapping functions inside a module can be merged along the way.

    Paper §3.6–3.7; App. C.4

Method 2

Self-Harness

Self-Harness: Harnesses That Improve Themselves

  • Zhang et al. · arXiv 2606.09498 v3 · 20 Aug 2026 (v1 8 Jun 2026)
  • Code: qzzqzzb/Self-Harness at 2720dbb

Lets the agent’s own model improve its harness, without human engineers or a stronger external agent. Each round mines failure patterns from the held-in traces, has the same model propose several small edits to declared parts of the harness, and keeps an edit only if it passes regression tests on a held-in and a held-out split. The search starts from a minimal benchmark-specific harness built on LangChain DeepAgents; each later round continues from the version accepted so far, while every task runs in a fresh environment.

How to read itThe proposer never sees held-out traces, but held-out pass counts decide promotion in every round, and the final held-out pass rates in the paper come from the same split. In evaluation terms that split therefore works as validation, not as an untouched final test. This is our reading, not the authors’ name for the split.

How to read itOnly the harness changes. The model’s weights are not trained.

One round

  1. Evaluate the current harness

    Run the fixed model inside the current harness on the held-in and held-out splits with the fixed evaluator, two attempts per task, and record each trace and its verifier outcome.

    Paper v3 §3.1–3.2; Alg. 1

  2. Mine weaknesses

    Give each failed held-in run a failure signature: the verifier-level cause, whether the agent’s behavior caused it, and the mechanism involved. Failures with the same signature are grouped into evidence clusters.

    Paper v3 §3.2

  3. Propose minimal edits

    The same model, now as proposer, sees the editable surfaces, the failure clusters, passing behavior to preserve and summaries of earlier attempts, but no raw logs and no held-out evidence. It returns several distinct, minimal edits.

    Paper v3 §3.3

  4. Build the candidates

    Each edit is applied to the harness definition, such as its instructions, subagents, skills, middleware or runtime policy. An edit that changes nothing is invalid.

    Paper v3 §3.3–3.4, §4.1

  5. Regression-test each candidate

    A candidate is accepted only if its pass count drops on neither split and rises on at least one. Trade-offs between the two splits, and candidates that fail to run, are rejected.

    Paper v3 §3.4; Alg. 1

  6. Merge and continue

    Compatible accepted edits are merged into the next harness; if none is accepted, the harness stays as it was. Every decision is logged.

    Paper v3 §3.4; Alg. 1

Method 3

Meta-Harness

Meta-Harness: End-to-End Optimization of Model Harnesses

  • Lee et al. · arXiv 2603.28052 v1 · 30 Mar 2026
  • Code: stanford-iris-lab/meta-harness at 8123cca

Searches over whole harness programs with a separate coding agent. The proposer, Claude Code with Opus 4.6, can selectively inspect the code, scores and raw execution traces of earlier candidates in a filesystem, and writes new single-file harnesses, from small edits to full rewrites of prompting, retrieval, memory and orchestration. The base model stays frozen.

How to read it“Online” text classification is a task protocol: labeled examples arrive one at a time, and the harness found by the search updates its memory as it was written to. The search itself runs beforehand, and no harness code is edited during that stream.

How to read itFor TerminalBench-2 the paper searches and evaluates on the same 89 tasks and calls it a discovery problem, so those results are not a held-out test.

One iteration

  1. Start the proposer

    A coding-agent session starts with a short human-written skill for the domain: where to write harnesses, how to inspect the history and which files are off limits.

    Paper §3

  2. Read the history

    The proposer browses a filesystem with the source code, search-set scores and execution traces of all earlier candidates and decides what to read. In the TerminalBench-2 run it read a median of 82 files per iteration.

    Paper §3; App. A.1

  3. Write new harnesses

    It diagnoses failure modes and writes k new single-file Python harnesses, either by editing an earlier one or by rewriting it.

    Paper §3; Alg. 1

  4. Validate the interface

    Each candidate has to pass interface validation before it is evaluated.

    Paper Alg. 1; App. D

  5. Score outside the proposer

    A fixed evaluator runs each valid harness with the frozen model on the search set. Its code, scores and traces are added to the filesystem; nothing is deleted.

    Paper Alg. 1; App. D

  6. Keep a frontier, evaluate once

    All evaluated candidates stay in a population with a Pareto frontier, for example accuracy against context tokens, and there is no fixed rule for choosing a parent. After a fixed number of iterations comes one final evaluation: the frontier on held-out test sets for classification, a single harness chosen by search-set performance on held-out problems for math, and the same 89 search tasks for TerminalBench-2, which the paper treats as a discovery setting. The proposer never sees test-set results.

    Paper §3; Alg. 1

How our harness is revisedFeedback → edit → selection, between evaluation rounds

  1. V1

    Hook-based search · frozen 9 Oct

    Feedback

    DeepSeek V4 Pro solves 100 development tasks three times per version. Compare same-task traces and group recurring failures, including exhausted budgets and missing final programs.

    Edit

    Parallel module lineages revise one allowed hook function at a time. Accepted loop, tool-use and completion edits encourage efficient exploration, verification and final submission.

    Selection

    Static checks, diff review and a two-task execution probe. Scores are recorded but do not decide promotion. Three search epochs are followed by integration and freezing.

  2. V2

    Scoped SDK search · frozen 13 Oct

    Feedback

    Sol solves, analyzes and edits; GLM-5.3-prime reviews. Dev100 is split into 80 proposal and 20 repeatedly used validation tasks, with three rollouts each. Strict replication rises from 183/300 in the seed to 191/300 in the observation candidate.

    Edit

    The retained edit changes ToolNode._normalize_tool_response in LangGraph. It preserves Python execution feedback and appends checks to consider for samples, specifications and inference.

    Selection

    After reviewing the development comparisons and execution traces, the team selected the observation candidate as experimental v2. Its source and configuration were frozen before the fresh paired evaluation.

Fixed boundary

The scorer, reference answers and evaluation budgets are not editable harness modules. Reference values are not given to the solving agent.

V1 archive · frozen 9 Oct 2026

V1 archive · the first frozen study

We adapted the ModularRSI idea to the DeepAgents harness that InferenceNet already uses and ran one complete evolution on a development set. This is a historical development study, frozen on 9 Oct 2026 and kept here with its original numbers. It is not a reproduction of the paper and not a leaderboard result, and it makes no claim about unseen tasks.

  • Paper

    ModularRSI

    The method and its reported results belong to the paper, which evolves five modules of the Terminus-2 harness (section 03).

  • Our adaptation

    Five hook functions

    Added to InferenceNet’s harness on unchanged DeepAgents 0.7.13: one edit per module per epoch, one function per module, no function library and no merge.

  • Development feedback

    100 tasks × 3 rollouts

    DeepSeek V4 Pro. The same tasks served for diagnosis and for the numbers below; promotion did not use the scores.

  • Held-out

    900 tasks · not run at the freeze

    Set aside before the run. In the 9 Oct 2026 snapshot the frozen harness had not been evaluated on them, so this page reports no generalization result.

  • Leaderboard

    A separate protocol

    All 1,000 tasks at half this study’s per-task budget. DeepSeek V4 Pro with DeepAgents scores 18.3% full replication there; the two numbers are not comparable.

Execution context

The study runs on DeepAgents 0.7.13, which assembles middleware, tools and backends and hands them to LangChain’s create_agent; LangGraph executes the loop. InferenceNet uses a lean configuration: no subagents, a StateBackend for notes and its own run_python tool, which starts a fresh sandbox for every call. DeepAgents itself is never edited. Three of the five evolvable functions run inside one middleware around each model call; tool_use adds guidance to the system prompt and the run_python description, and observation reshapes the feedback run_python returns, as section V1.1 shows.

All five start as no-ops, so the initial harness is unchanged DeepAgents. It runs with this study’s budget and sandbox, not phase 1’s: 12 model calls and 8 run_python calls per task instead of 6 and 4.

V1.2 / Evolution run

How one evolution run works, step by step

Five module lineages start from the same no-op source and the same initial trajectories. Each lineage may change only its own function. The loop below ran three epochs, then combined the accepted functions into one frozen harness.

  1. 01

    Split the tasks before anything runs

    From the 1,000 Selected_1000 tasks, 100 become the development set and 900 are held out. Tasks from the same paper or with identical input files stay on the same side. The evolution loop never dispatches the 900 held-out tasks.

    Development tasks
    100
    Held-out tasks
    900 · not run as of 9 Oct 2026
  2. 02

    Roll out every harness version

    Each harness version solves every development task three times with DeepSeek V4 Pro inside DeepAgents. Every run_python call starts a fresh sandbox; nothing persists between calls.

    Rollouts per evaluation
    300
    Budget per rollout
    12 model calls · 8 run_python calls
    Output and time limit
    32,768 tokens · 30 min
    Sandbox per call
    6 GB · 2 CPUs · 90 s
  3. 03

    Score in private

    The evaluator reruns each final program from scratch and compares its output with the reference values. The model, the analyst and the editor never see those values or the scorer internals. The scorer is independent of the agent, but it scores the same development tasks that the analyst diagnoses, so these scores are not an independent validation.

  4. 04

    Diagnose by contrast

    Tasks are grouped by outcome across their three rollouts: all passed, mixed or all failed, where a pass means the coefficient and SE are within 5%. An analyst model reads all 100 tasks in ten batches of ten. In a mixed task it compares passing and failing rollouts; in an all-failed task it compares an earlier version’s passing rollout of that task when one exists, and otherwise reads the failures on their own; in an all-passed task it looks for wasted steps. A problem needs support from at least two different tasks in one batch, and the batch finding with the most supporting tasks drives the edit.

    Same-task comparisons remove most task difficulty, but they need a passing rollout of the same task: only 21 of 100 tasks were mixed at the start. In this run, 17 of the 24 task votes behind the eight promoted edits came from tasks that failed all three rollouts and were diagnosed without a comparison.

  5. 05

    Edit one function

    For each lineage, an editor model sees only its function, the history of accepted versions and the selected finding. It returns a new version of that function. Static checks verify syntax, imports, the interface and the editing scope.

  6. 06

    Review the diff, then probe on real tasks

    A reviewer model rejects changes that are not general across tasks, such as ones that encode task-specific details. The candidate then runs two real development tasks. If the probe completes without protocol or runtime errors, the candidate is promoted.

    Promotion does not look at development scores. The scores in section V1.3 are recorded for analysis only, so an accepted version can score lower than its parent. The two-task probe shows that a candidate runs end to end; it is not a statistical test that performance held.

  7. 07

    Repeat for three epochs

    Each module gets at most one edit per epoch. A promoted version becomes the parent for the next epoch, and every promoted version receives a full 300-rollout evaluation.

    Candidate slots
    15
    Promoted
    8
    Rejected by diff review
    3
    Editor output or edit invalid
    4
  8. 08

    Integrate, refine once, freeze

    The accepted versions of agent_loop, completion and tool_use are combined and probed together. One integration epoch reads the combined trajectories and makes a single checked refinement. The result is frozen by hash before any held-out evaluation.

    Changed modules
    3 of 5
    Frozen source
    17f138b9

What did not work

  • Accepted is not the same as better. In completion, epochs 2 and 3 reached 84 and 85 full replications, below epoch 1’s 95; in tool_use, epoch 3 reached 87, below epoch 2’s 91.
  • Two modules never changed. All three observation candidates and all three context candidates were rejected: two by diff review, three for invalid editor output and one for failed checks. The best-supported finding of the run, “Empty listing for present data” with 9 supporting tasks, was rejected by diff review.
  • More scored results, not more precise ones. Among rollouts with a scored final result, the share with full replication fell from 47.4% to 41.9% between the initial and the frozen harness.
  • Some signals barely moved or got worse. “A tool execution timed out” went from 4 to 5 tasks, and “Same failure type repeated, mostly no result file” from 75 to 72 tasks (section 05.4).
  • Thin evidence per edit. Each promoted edit rested on 2 to 5 supporting tasks, and 17 of the 24 task votes behind the eight promoted edits came from tasks that failed all three rollouts and were diagnosed without a comparison (step 04).

Most of the gain comes from more rollouts finishing with a program the evaluator can score: 171 → 217 of 300. Among scored rollouts, the full-replication share fell from 47.4% to 41.9%. The evolved harness mainly fixed how runs end; it did not make the statistics more precise.

These results are not part of the leaderboard and are not comparable with it: each rollout here may use 12 model calls and 8 run_python calls, twice the leaderboard’s 6 and 4, in a different sandbox and on a 100-task development subset. V1.5 / Evolved code

What the frozen functions say

All five functions started as no-ops: tool_use and completion returned an empty string, agent_loop never intervened. Below are the three functions that changed, exactly as frozen. observation and context are unchanged.

tool_use.py · 3 epochs + 1 refinement
"""Model-visible Python-tool guidance hook."""


def tool_use() -> str:
    """Return additional general tool-use guidance, if any."""
    return (
        "Use tool calls efficiently. Prefer combined or batched operations, inspect data "
        "shape and dtypes in few calls, and verify final programs with targeted unit tests "
        "rather than repeated exploratory calls. Plan a multi-phase call budget before starting: "
        "allocate a bounded number of calls for initial data inspection, one consolidated call "
        "for exploratory diagnostics or transformations, and always reserve at least two calls "
        "for executing and validating the final program. Never spend exploratory calls on "
        "information you can derive from existing outputs or task context. If a call budget is "
        "available, reserve enough calls for final verification. When a tool call returns only a "
        "signature echo, runtime warning, empty result, or indicates an unavailable tool or file, "
        "do not retry the same call or rely on it for critical specification details. Instead, "
        "reason from information already present in existing outputs, task description, or any "
        "attached artifacts, and proceed with the most direct, defensible next step. When "
        "filesystem inspection is unavailable, prefer direct artifact-independent implementation "
        "and inference from available context to avoid stalled exploration. Before making a final "
        "submission, execute the full solution program at least once and verify it completes "
        "without error, rather than submitting unexecuted code or prose."
    )
completion.py · 3 epochs
"""Final-answer guidance hook."""


def completion(remaining_model_calls: int) -> str:
    """Return a bounded reminder about complete program submission, if any."""
    if remaining_model_calls > 1:
        return (
            "If you have verified your complete program, submit it now. "
            "If you have not yet verified it and still have tool or execution attempts available, "
            "continue debugging instead of submitting an unverified program. "
            "After any tool call or execution attempt, always finish your turn with an assistant "
            "message summarizing the result before waiting for another step."
        )
    if remaining_model_calls == 1:
        return (
            "You have one model call remaining. Use it to submit your complete program only if it is "
            "already verified. If it is not verified, you may still use remaining tool or execution "
            "attempts to debug before your final submission. End every turn with a final assistant "
            "completion after tool calls so your verified result is captured by the harness."
        )
    return (
        "Submit your complete program now. End this turn with a final assistant completion so "
        "the submitted program is recorded as your final answer."
    )
agent_loop.py · 2 accepted epochs
"""Agent-loop decision hook; edited versions must retain this interface."""


def agent_loop(remaining_model_calls: int, last_tool_failed: bool) -> dict[str, bool]:
    """Return final-only and repair decisions for the next model request.

    Budget-conscious scheduling: when the model can no longer afford a
    meaningful followup cycle, the loop stops issuing exploratory calls and
    asks for a final result.  A recent tool failure only triggers a repair
    nudge while there is enough budget remaining to act on it.

    Repeated tool failures are treated as a stronger signal that the current
    computation path is unproductive.  This prevents the loop from burning the
    remaining budget on redundant retries; instead it forces finalization so
    the model must consolidate whatever partial or negative result it has
    accumulated before tool-call exhaustion.
    """
    can_afford_followup = remaining_model_calls > 1

    # With only one call left there is no room for a repair plus a final
    # answer, so finalization is forced regardless of tool state.
    if not can_afford_followup:
        return {"force_final": True, "repair_nudge": False}

    # With two calls remaining, a repair nudge is only useful if the model
    # has not already consumed the budget on failed repair attempts.  In that
    # case the loop should stop nudging and force a final consolidation.
    if last_tool_failed and remaining_model_calls <= 2:
        return {"force_final": True, "repair_nudge": False}

    # Otherwise the failure can still be repaired while preserving a final call.
    force_final = False
    repair_nudge = last_tool_failed and can_afford_followup

    return {"force_final": force_final, "repair_nudge": repair_nudge}

Full replication requires the coefficient and standard error within 1% relative error and the p-value within 0.01 absolute error (local-paper-v1). Method: ModularRSI by Wu et al. (arXiv 2609.14857 v1, 14 Sep 2026). This adaptation keeps the five-module split, contrastive trajectory diagnosis, scoped edits, diff review, execution probes and integration. Unlike the paper, it evolves on 100 InferenceNet development tasks rather than a separate evolution set, makes at most one edit per module per epoch rather than per batch, edits one entry function per module rather than a library of variants, and implements neither function merge nor task-aware function composition. The paper evolves a Terminus-2-based harness; this study evolves hook functions around unchanged DeepAgents 0.7.13.
