Research directions

What should agents learn from these challenges?

The task demonstrations across econometric replication and business analysis lead to four questions about the capabilities behind reliable agent work.

  • Statistical reasoning

    How do research requirements become the right analysis?

    Understand the requested method and constraints, then carry them into sample selection, model specification and statistical inference.

  • Data interpretation

    How can an agent understand unfamiliar data?

    Use task materials and data evidence to identify what each observation represents, how variables are coded, and what units and groups mean.

  • Feature construction

    How can it construct and verify the right variables?

    Turn the research question into justified transformations, scaling and interactions. Check their meaning against the task and data, alongside checking that the code runs.

  • Deliverable verification

    How do multi-file findings become traceable reports and workbooks?

    Reconcile rules and records across source documents, preserve live calculation formulas in spreadsheets, and verify that reports and workpapers agree before submission.

Well-specified tasks provide the background and data clues needed for these judgments. Ambiguous variable definitions and rubric edge cases also inform improvements to task design and evaluation.

Two paths for developing these capabilities

01 / Model training

Learn from verified analyses and execution traces

Study how supervised fine-tuning, distillation and reinforcement learning can teach models to interpret data, plan analyses, use tools and verify their work. Use verified training tasks and evaluate the learned capabilities on held-out tasks.

02 / Model–Harness co-evolution

Improve model capabilities and harness behavior together

Explore alternating model updates with improvements to planning, tools, context and evidence checks. Compare model-only, harness-only and joint changes on held-out tasks under the same evaluation conditions.

Where our harness work stands — and what changes next

Phase 1 · Completed on Econometric Replication

From submission recovery and audit guidance to executable diagnostics

Our current four-harness Dev100 comparison and the ModularRSI study below were conducted in Phase 1 on econometric replication tasks in InferenceNet’s run_python sandbox. ModularRSI evolved submission-policy hooks and statistical-audit feedback in LangGraph’s ToolNode, raising strict replication from 64% to 67% with GPT-5.6 Sol. The next step for Subtrack 1 is upgrading static text guidance to executable diagnostic hooks that automatically inspect sample attrition, collinearity drops, cluster granularity and unit scaling before final submission.

Phase 2 · Planned for Finance & HR (Harbor + Claude Code)

Adapting harness checks and evolution to Harbor

Subtrack 2 (Business Analysis & Deliverables) has not yet undergone harness optimization. Its tasks currently run on the Harbor (0.20.0) evaluation framework driving Claude Code (2.1.114), where pilot errors stemmed from missing Excel formulas, cross-file count mismatches and rubric misclassifications. We plan to adapt our modular harness hooks and evolution loop to the Harbor + Claude Code workflow—adding pre-submission readback checks for spreadsheet formulas (.xlsx), report-to-workbook consistency (.docx/.xlsx) and source-evidence indexing.

These are research directions. The InferenceNet ModularRSI study below evolves the harness on econometric replication tasks while keeping model weights fixed.

01 / Concept

What self-evolution changes, and what it leaves alone

Harness self-evolution, also called automatic harness optimization, means proposing, testing and keeping harness versions on the basis of feedback from the harness’s own runs. The three methods detailed on this page do this in offline rounds: an outer loop edits the harness between evaluations, and the model’s weights do not change. That is how these three work, not a limit of the idea. Other methods change the harness across a stream of tasks, during a single run or for each task instance, and some also train the weights; the research map below places them.

  • Fixed

    Model

    The language model and its weights. Within a controlled harness comparison, both versions use the same solving model. Separate searches may use different frozen solving or proposer models, and must be identified separately. Methods that train model weights are another branch on the research map.

  • Edited

    Harness

    The software that runs the model as an agent: the loop, tool definitions, how observations are shown, how context is kept, prompts, memory and when to stop. This is what the loop changes, as a whole or in parts.

  • Observed

    Agent

    The model running inside one harness version on one task. Its trajectories and outcomes are the evidence the loop learns from.

  • Scoped

    SDK

    The libraries that implement the agent runtime. Our ModularRSI adaptation uses a pinned copy of DeepAgents, LangChain and LangGraph with scoped hook and source edits, while model weights and the evaluator remain fixed.

  • Fixed

    Environment

    What the tools act on: tasks, data, files, sandboxes. It is held constant so that a change in score can be traced to the harness.

  • Fixed

    Evaluator

    The scorer that grades finished runs. It decides which version looks better, so it is never among the things edited; methods differ in how much of its output the proposer may see.

The editable boundary must be recorded per method and release. All results below retain their original task split, budget caps and selection policy.

Research map · 2025–2026

When the harness changes, and what decides

Methods in the four lanes below run an agent, read feedback from those runs, edit part of the harness and keep some of the edits. They differ in when that happens: between rounds on a task set, across a stream of new tasks, within one continuing run, or once per task instance. The lanes are alternatives, not stages of a history. Around them sit routes that change or describe something else: a branch that also trains model weights, systems that compose several harnessed agents, the representation a harness is written in, and the evaluation that scores it.

Self-evolution

Run, record, select

Self-evolving methods wrap the run in an outer loop: what each round records becomes proposed harness edits, and only candidates that pass the check carry forward.

  1. L1

    Run

    The current harness version works through tasks and records every step.

    • Task stream
    • Current harness
  2. L2

    Record and propose

    Traces, scores and failures are collected, and a proposer writes candidate edits to the harness.

    • Traces
    • Scores
    • Candidate edits
  3. L3

    Check and select

    Candidates are evaluated, and the selected version becomes the harness for the next round.

    • Evaluation
    • Selected version

02 / Improvement loop

One loop behind all three methods

The methods differ in how much of the harness they open up, who writes a change and how a candidate is judged. Each iteration still has the same five steps, and the candidates evaluated so far, with their run evidence, inform the proposals of the next round.

In these three methods the search runs offline

In all three methods, versions are proposed and selected between evaluation rounds, and the result is frozen before it is evaluated or used. When an evaluation feeds tasks as a stream, as in Meta-Harness’s online text-classification setting, that describes how the application receives its inputs. It does not mean the harness edits itself while it runs.

Two methods on the research map differ on exactly this point: Evo-Harness updates its harness between the tasks of a stream, and Continual Harness edits it during a single run.

Six questions to ask of any method

  1. Which part of the harness may change?
  2. Who proposes the change?
  3. Which trajectories and feedback does the proposer see?
  4. How is a candidate accepted, merged or rejected?
  5. When does the search run, and is the result frozen before use?
  6. What stays fixed: model, environment, evaluator, tasks?

03 / Methods

Three offline methods in detail

ModularRSI, Self-Harness and Meta-Harness come from different groups and are separate methods. Each mechanism summary follows the paper and its official repository, tracing one iteration of the method’s improvement loop.

Method 1

ModularRSI

ModularRSI: Modular and Generalizable Recursive Harness Self-Improvement

  • Wu et al. · arXiv 2609.14857 v1 · 14 Sep 2026
  • Code: IQuestLab/ModularRSI at b5c72c3

Evolves a Terminus-2-based harness one module at a time. The agent’s own model contrasts passing and failing rollouts of the same task on evolution tasks curated apart from the evaluation benchmarks, then changes functions inside one of five modules: agent loop, tool use, observation management, context management and task completion detection. The evolved modules are integrated and frozen before any benchmark evaluation.

One iteration

  1. Roll out on evolution tasks

    Run the current harness K times on each task of a batch of evolution tasks. The paper curates 2,000 executable evolution tasks that do not overlap with the evaluation benchmarks and uses 240 of them in its main experiments. Each task’s own tests mark every rollout as passed or failed.

    Paper §3.3, §5.3

  2. Sort tasks by outcome

    Tasks with mixed results pair a passing with a failing rollout. Tasks that always fail look up an earlier success in a trajectory memory, or are diagnosed on their own. Tasks that always pass are checked for wasted steps.

    Paper §3.3, Eq. 1

  3. Diagnose against one module

    The Code-Modify Agent, run by the same model, reads the trajectories, finds where the passing and failing rollouts diverge and asks whether a change to the module under evolution would have changed the outcome.

    Paper §3.3; App. B, C.1

  4. Rank candidate changes

    Findings that target the same function are merged into one candidate, whose vote count is the number of distinct tasks supporting it. An evolution history of earlier changes helps avoid repeated or contradictory edits.

    Paper §3.4

  5. Write one scoped change

    The agent writes one change that has to hold for all supporting findings, by adding, modifying or replacing a function variant, and it may write only inside that module.

    Paper §3.4; App. C.2

  6. Pass three gates or roll back

    A program check of syntax, imports and protocol; a diff review that does not see rewards and rejects task-specific code; an execution check on two tasks sampled from the current batch. A change that fails any gate is rolled back, and one that passes becomes the next generation.

    Paper §3.5; App. C.3

  7. Integrate and freeze

    After three epochs per module, the five modules are combined and one integration epoch repairs cross-module conflicts; then the function library is frozen. Overlapping functions inside a module can be merged along the way.

    Paper §3.6–3.7; App. C.4

Method 2

Self-Harness

Self-Harness: Harnesses That Improve Themselves

  • Zhang et al. · arXiv 2606.09498 v3 · 20 Aug 2026 (v1 8 Jun 2026)
  • Code: qzzqzzb/Self-Harness at 2720dbb

Lets the agent’s own model improve its harness, without human engineers or a stronger external agent. Each round mines failure patterns from the held-in traces, has the same model propose several small edits to declared parts of the harness, and keeps an edit only if it passes regression tests on a held-in and a held-out split. The search starts from a minimal benchmark-specific harness built on LangChain DeepAgents; each later round continues from the version accepted so far, while every task runs in a fresh environment.

One round

  1. Evaluate the current harness

    Run the fixed model inside the current harness on the held-in and held-out splits with the fixed evaluator, two attempts per task, and record each trace and its verifier outcome.

    Paper v3 §3.1–3.2; Alg. 1

  2. Mine weaknesses

    Give each failed held-in run a failure signature: the verifier-level cause, whether the agent’s behavior caused it, and the mechanism involved. Failures with the same signature are grouped into evidence clusters.

    Paper v3 §3.2

  3. Propose minimal edits

    The same model, now as proposer, sees the editable surfaces, the failure clusters, passing behavior to preserve and summaries of earlier attempts, but no raw logs and no held-out evidence. It returns several distinct, minimal edits.

    Paper v3 §3.3

  4. Build the candidates

    Each edit is applied to the harness definition, such as its instructions, subagents, skills, middleware or runtime policy. An edit that changes nothing is invalid.

    Paper v3 §3.3–3.4, §4.1

  5. Regression-test each candidate

    A candidate is accepted only if its pass count drops on neither split and rises on at least one. Trade-offs between the two splits, and candidates that fail to run, are rejected.

    Paper v3 §3.4; Alg. 1

  6. Merge and continue

    Compatible accepted edits are merged into the next harness; if none is accepted, the harness stays as it was. Every decision is logged.

    Paper v3 §3.4; Alg. 1

Method 3

Meta-Harness

Meta-Harness: End-to-End Optimization of Model Harnesses

  • Lee et al. · arXiv 2603.28052 v1 · 30 Mar 2026
  • Code: stanford-iris-lab/meta-harness at 8123cca

Searches over whole harness programs with a separate coding agent. The proposer, Claude Code with Opus 4.6, can selectively inspect the code, scores and raw execution traces of earlier candidates in a filesystem, and writes new single-file harnesses, from small edits to full rewrites of prompting, retrieval, memory and orchestration. The base model stays frozen.

One iteration

  1. Start the proposer

    A coding-agent session starts with a short human-written skill for the domain: where to write harnesses, how to inspect the history and which files are off limits.

    Paper §3

  2. Read the history

    The proposer browses a filesystem with the source code, search-set scores and execution traces of all earlier candidates and decides what to read. In the TerminalBench-2 run it read a median of 82 files per iteration.

    Paper §3; App. A.1

  3. Write new harnesses

    It diagnoses failure modes and writes k new single-file Python harnesses, either by editing an earlier one or by rewriting it.

    Paper §3; Alg. 1

  4. Validate the interface

    Each candidate has to pass interface validation before it is evaluated.

    Paper Alg. 1; App. D

  5. Score outside the proposer

    A fixed evaluator runs each valid harness with the frozen model on the search set. Its code, scores and traces are added to the filesystem; nothing is deleted.

    Paper Alg. 1; App. D

  6. Keep a frontier, evaluate once

    All evaluated candidates stay in a population with a Pareto frontier, for example accuracy against context tokens, and there is no fixed rule for choosing a parent. After a fixed number of iterations comes one final evaluation: the frontier on held-out test sets for classification, a single harness chosen by search-set performance on held-out problems for math, and the same 89 search tasks for TerminalBench-2, which the paper treats as a discovery setting. The proposer never sees test-set results.

    Paper §3; Alg. 1

InferenceNet ModularRSI: implementation and results

How ModularRSI evolves the DeepAgents harness

  1. 01 · Exploration & completion modules

    Budget-aware exploration and final submission

    Evolves the agent_loop, tool_use and completion modules so the agent batches exploratory data checks, reserves calls for verification, and submits a complete Python program before budget exhaustion.

  2. 02 · Runtime integration

    Scoped SDK wiring

    Integrates the evolved submission and tool-guidance policies directly into the pinned DeepAgents and LangChain model-binding path so they execute deterministically on every turn.

    Inspect the SDK integration →
  3. 03 · Observation module

    Statistical-audit execution feedback

    Evolves ToolNode._normalize_tool_response in LangGraph to enrich run_python outputs with structured statistical-audit checks covering sample filtering, model specification and standard-error clustering.

How our harness is revisedFeedback → edit → selection, between evaluation rounds

  1. Loop & submission

    Module hook search

    Feedback

    Roll out the harness three times per task on Dev100. Contrast passing and failing traces on the same task to isolate recurring failures such as exhausted call budgets and missing final programs.

    Edit

    Parallel module lineages revise one scoped function at a time (agent_loop, tool_use, completion) to enforce efficient data inspection, verification and final program submission.

    Selection

    Candidates must pass static syntax/interface checks, reward-blind diff review and a two-task execution probe before integration into the runtime.

  2. Observation audit

    Scoped runtime search

    Feedback

    Analyze execution traces where programs ran and submitted output but missed strict replication due to sample construction, fixed effects or clustering mismatches (183/300 → 191/300 across development rollouts).

    Edit

    Modify ToolNode._normalize_tool_response in LangGraph to preserve raw Python execution output while appending targeted verification prompts for sample scope, specification and inference.

    Selection

    Select the non-regressive candidate on development validation and freeze all module and SDK source hashes prior to the paired Dev100 evaluation.

Fixed boundary

The scorer, reference answers and evaluation budgets are not editable harness modules. Reference values are never shown to the solving or editing agent.
